## 1. システム構成

```
ブラウザ(HTML / CSS / JavaScript)
   ↕ REST API(JSON)
Java(Spring Boot + Spring Security)
   ↕ JPA(Hibernate)
SQLite
```

| 項目 | 採用技術 | 備考 |
|------|----------|------|
| フロントエンド | HTML / CSS / JavaScript | フレームワークなしの素のJSを想定 |
| バックエンド | Java(Spring Boot) | REST APIを提供 |
| 認証 | Spring Security | セッション認証(メールアドレス+パスワード) |
| DB | **SQLite** | JPAで抽象化し、将来PostgreSQLへ移行可能な設計とする |
| 発音再生 | Web Speech API | ブラウザ標準機能。音声ファイル・サーバー負荷なし |

### 処理の役割分担

- **類似度判定:** フロントエンド(JavaScript)で計算 — 即時表示のため
- **習熟度の計算・保存:** バックエンド(Java)で実施 — 改ざん防止と一元管理のため

## 2. 画面設計

### 2.1 画面一覧

| # | 画面 | 内容 |
|---|------|------|
| S0 | ログイン / 新規登録 | メールアドレス+パスワード |
| S1 | ホーム / レベル選択 | TOEICスコア帯(400/600/800/900+)を選択し学習開始 |
| S2 | クイズ画面 | 例文穴埋め、入力欄、ヒントパネル(5種)、類似度%表示 |
| S3 | 結果表示 | 正解、類似度、習熟度の変化(S2内のオーバーレイ表示とし、テンポを重視) |
| S4 | 単語一覧 / 習熟度 | 単語ごとの習熟度をリスト表示 |

### 2.2 画面遷移

```
S0 ログイン ──→ S1 ホーム / レベル選択 ←──→ S4 単語一覧 / 習熟度
                     │
                     ▼
               S2 クイズ画面 ←─┐
                     │         │ 次の問題
                     ▼         │
               S3 結果表示 ────┘
```

### 2.3 クイズ画面(S2)の構成要素

- 例文表示エリア(対象単語を「_____」で伏せ字)
- 解答入力欄・解答ボタン
- 類似度%表示エリア
- ヒントパネル:定義 / 類義語 / 発音 / シャッフル / イラスト の5ボタン(押すと展開)
- 使用済みヒント数の表示

## 3. REST API設計(概要)

| メソッド | パス | 内容 | 認証 |
|---------|------|------|------|
| POST | /api/auth/register | 新規登録 | 不要 |
| POST | /api/auth/login | ログイン | 不要 |
| POST | /api/auth/logout | ログアウト | 要 |
| GET | /api/words?level=600 | レベル別の出題単語取得 | 要 |
| POST | /api/quiz/answer | 解答送信(単語ID、入力値、使用ヒント)→ 判定結果と更新後習熟度を返却 | 要 |
| GET | /api/mastery | 自分の習熟度一覧 | 要 |

リクエスト/レスポンスの詳細JSON仕様は詳細設計で定義する。

## 5. コアロジックの方針

### 5.1 類似度判定(フロントエンドJS)

- レーベンシュタイン距離(編集距離)をベースにしたカスタム実装
- **r ↔ L の置換**は通常の置換より低コスト(軽いミス扱い)
- **隣接位置の文字のズレ**(前後繋がりのミス)も低コスト扱い
- 類似度% = (1 − 正規化編集距離) × 100
- 具体的なコスト値・計算式は詳細設計で定義する

### 5.2 習熟度(バックエンドJava)

- 習熟度は 0〜100 のスコア
- 加算量 = 基礎点 × 類似度 × (1 − ヒントペナルティ合計)
- ヒント1つ使用ごとにペナルティが増加(ヒント種類ごとのペナルティ値は詳細設計で定義)

## 6. セキュリティ・非機能

- パスワードは BCrypt でハッシュ化して保存
- 認証系を除くAPIはログイン必須
- Web公開時はHTTPS前提
- SQLiteは同時書き込みに弱いため、ユーザー数が数百人規模に達した場合はPostgreSQLへの移行を検討する(JPAによる抽象化で移行コストを最小化)
